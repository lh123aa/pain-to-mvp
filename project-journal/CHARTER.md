# 立项宪章 · pain-to-mvp 痛点→MVP机会发现管线

> 项目 slug：`pain-to-mvp` · 创立日期：2026-10-15 · 基准货币：CNY
> 本文件定义"这个项目要做成什么"和"什么算成功、什么算失败"。**成功线/止损线一旦写下就不轻易改动** —— 它是防止自我美化的唯一客观标尺。

## 1. 一句话目标
从B站评论挖真实痛点，产出可执行的MVP机会报告；做成可售工具/服务

## 2. 为谁解决什么问题
- 目标人群：独立开发者 / 微创业者 / 想找"已验证需求"再动手做产品的人（判断：由项目自身关键词「独立开发者怎么接单」与 PRD 场景推断，待真实用户验证）
- 他们的痛点（要具体到场景）：想做产品但不知道做什么；判断需求靠手工刷 B站/知乎 评论，耗时且样本偏差，看完一堆评论仍拿不准"这事值不值得做"
- 现在的替代方案（他们现在怎么凑合）：手工刷评论区、问朋友、拍脑袋立项；或买泛泛的行业调研报告（粒度太粗、无一手证据）
- 为什么我会做得更好：全管线自动化（发现→清洗→聚类→评分→报告），且**每个结论可反推核对**——报告含决策漏斗、分数拆解、被过滤评论逐条理由、实际召回视频标题，证据链完整

## 3. 变现假设（谁 + 痛 + 愿意付多少 + 凭什么判断）
- 谁：独立开发者 / 微创业者（同 §2）
- 愿意付多少：`待确认`（无实测数据，不编造；候选形态：单份机会报告付费 / 工具订阅）
- 判断依据：`待确认` —— 现有依据仅是 PRD 立项假设 + B站真实痛点数据存在（问题域痛点率 23.6%），尚无任何付费意愿证据
- 验证方式（怎么用最小成本验证）：校准闭环（#11）先证明结果可信 → 再用 3-5 份真实报告找目标用户换反馈，探测付费意愿后再定价

## 4. 成功线（达成即算变现成功，写客观可查的标准）
累计20条抽检记录、top3推荐命中率≥70%

来源：PRD §五（Q6）既有验收标尺，2026-10-15 用户确认沿用。当前进度：2/20 条抽检记录（`data/calibration/`）。
（注：命中率是"结果可信"的门槛——工具级可信之后才谈售卖；售卖阶段的收入线届时另行补写并记录变更理由）

## 5. 止损线（触发即停止投入，不允许"再试一个月"）
连续2周无阶段推进即暂停并复盘去留

"阶段推进"= 看板上阶段 4-6 任一阶段状态从 ⬜/🔨 变 ✅（有可展示的完成物 + 测试绿 + 入档），2026-10-15 用户确认。

## 6. 关键约束
- 时间预算：每周 __ 小时（待确认）
- 资金预算：累计不超过 __（待确认；当前无外部付费依赖，API key 缺失时走启发式路径）
- 不可触碰的底线（合规/道德/健康）：
  - 爬取合规红线（已写入代码与测试）：robots.txt fail-close 不得封死 B站主路径；`v_voucher` 只报错不绕过；Layer 1 域预检只警告不阻断；不开发任何绕过平台限制的手段
  - 报告正文禁 emoji 作图标（码位防线含 0x2600-0x27BF / 0x2B00-0x2BFF / FE0F）
  - 记录不写入密钥与隐私

## 7. 明确不做（防止范围蔓延）
- 不做 LLM 强依赖：缺 API key 全程走启发式，评分证据驱动（无证据的维度留 `None`，不硬凑）
- 不做"自优化"定时任务投入（PRD §三 Q3 决策：daily-audit 去定时改手动，#14 待清）
- 不做爬虫绕过与反检测能力（见 §6 红线）
- 不做通用社交媒体分析：只做 B站 → 中文机会发现这一纵深

## 8. 风险与依赖（最可能让项目死掉的 3 件事）
1. B站接口/合规环境变化（`v_voucher`、robots、反爬升级）使数据源失效 —— 单点依赖，无备用数据源
2. 校准不收敛：命中率停在 70% 以下 → 成功线永远够不着 → 触发止损（当前实测曾出现 50%，A5 修复后待复检）
3. 维护性损耗：apply_fixes 回退陷阱（#27）这类"改一处必须同步三处"的耦合持续消耗迭代速度
