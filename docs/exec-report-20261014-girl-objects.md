## 2. 决策漏斗：270 条 → 3 张卡

```
270   爬取到的评论（15 视频中 11 个有评论）
 ├─清洗（去空/去无效）      -15  → 255
 ├─跨视频文本去重            -3  → 252
 ├─🎯 主题聚焦               未启用 ← run_all 不传 --topics，T10 功能未接线
 ├─痛点过滤 pain_score ≥ 3  -194  → 58   ★ 最大过滤器：76% 评论在这里消失
 └─聚类 min_size ≥ 3         -5  → 53 成员 / 3 簇
                               ↓
                             3 簇 → 3 张卡
```

**为什么 194 条在痛点过滤层消失**：`filter_painful(min_score=3)` 用**规则词表**给
每条评论打 `pain_score`（`pain_rules.py:79`）——命中「多少钱/价格/收费/贵」等付费词、
「太难了/不会/不懂」等困惑词才得分。闲聊、纯情绪、无规则词命中的评论得 0~2 分被丢弃。
本次 270 条里只有 58 条命中至少 3 分。

**为什么 5 簇只剩 3 簇**：TF-IDF + KMeans 定簇数 `n = min(5, max(2, 58//5)) = 5`，
聚出 5 簇后 `min_size=3` 把只有 1~2 条的小簇丢掉（共 5 条评论）。

## 3. 每步的判断规则（代码级）

### 3.1 簇的主题为什么是「求助」
`mine_pain_points.py:126`
```python
top_signal = max(sig_counter.items(), key=lambda kv: kv[1])[0]   # 取频次最高的信号
pain_summary = f"{size}条评论集中反映「{top_signal}」：{best_quote}"
```
簇1 信号分布 `求助 25 / 困惑 10 / 期望 8 / 对比 5 / 失望 4 / 抱怨 3 / 付费意愿 1`
→ 「求助」频次最高 → 主题定为求助，代表句取 `quotes[0]`。
**规则含义：说的人多 ≠ 值钱**。求助类评论（求加群、求教程）天然量大，恒压过付费/失望类。

### 3.2 代表原话为什么是 300 字长文
`cluster.py:71-83` 代表句 = `avg × (0.5 + 0.5 × pain/max_pain)` 乘性打分 + MMR 去冗余。
**没有任何长度上限** → 一段 300 字的个人经历只要簇相关度高就登顶，直接进卡片。

### 3.3 分数为什么是 80（已精确反推验证）
`score_opportunity.py`
```python
demand     = clamp(round(avg_pain/2 + (1 if 付费意愿 else 0)), 1, 5)
feasibility= 5 if size < 50 else (4 if size < 200 else 3)   # ← 纯由簇大小决定
competition, reach, ai_leverage = None, None, None          # ← 启发式路径恒为 None

total = ((demand + feasibility)/2) / 5 * 100 × min(1.0, 0.6 + 0.04×size)
```
`_compose_total`（第 90 行）取**有效维度均值**——3 个 `None` 维度被除数剔除，
**5 个维度实际只有 2 个参与打分**。

本次 3 张卡全部精确复现：

| 簇 | size | avg_pain | demand | feasibility | raw | conf | total | 档 |
|---|---|---|---|---|---|---|---|---|
| 1 | 43 | 4.28 | 3（含付费意愿+1） | 5（43<50） | 80 | 1.00 | **80.0** | A |
| 2 | 7 | 5.00 | 2 | 5（7<50） | 70 | 0.88 | **61.6** | B |
| 3 | 3 | 5.67 | 3 | 5（3<50） | 80 | 0.72 | **57.6** | B |

档位：≥85 S ｜ ≥70 A ｜ ≥55 B ｜ ≥40 C ｜ 其余 D。

**结论：80 分 A 档 = 「中等痛点强度 + 簇小」的算术结果，与"是不是真机会"无关。**
`feasibility` 满分只因 43 < 50；`conf` 满分只因 43 ≥ 10（`0.6+0.04×43=2.32` 被截到 1.0）。

### 3.4 MVP 为什么三张卡一模一样
`design_mvp.py:39, 46`
```python
sigs = list(pain.get("signal_distribution", {}).keys())   # ← dict 插入顺序，非按频次排序
for s in sigs:
    if s in SIGNAL_TO_MVP: recommended.append(...)
deliverable_hint = recommended[0]["type"]                 # ← 取第一个匹配的键
```
**它不看主导信号、不看频次，看的是信号 dict 的第一个键**。
本次三张卡 `signal_distribution` 的第一个键**恰好都是「求助」**（`SIGNAL_TO_MVP["求助"]`
= 模板/提示词库）→ 三张卡 `推荐类型` 全同。

其余字段 `validation_plan` / `revenue_layers` / `tech_stack` / `estimated_cost`
是**硬编码常量**，每张卡必然相同。

### 3.5 评分理由为什么显示「启发式评分」
`score_reason` 实际为 `None`（启发式路径不生成理由），卡片用
`p.get('score_reason', '启发式评分')` 兜底 → **卡片上那行是兜底文案，不是真实理由**。

### 3.6 卡片为什么会被覆盖
`export_card.py` 的 `card_id = 今日日期-序号`（序号按 `enumerate` 从 1 起）。
同日第二次跑会从 `001` 重新编号 → **静默覆盖前一次的卡片文件**。
实测：`20261014-001` 从 15:25（上一轮"独立开发者"）被覆盖成 18:07（本轮）。
