# Pain-to-MVP 探矿仪：修复与首跑设计

日期：2026-10-11
状态：已获口头批准（"开始制作"）
作者：与用户对话推导

---

## 一、意图与为什么

用户要把这套系统当**探矿仪**用：输入一个关键词，从真实平台评论区挖出可信的痛点，输出可执行的机会卡片——用来验证已有项目的商业价值，或发现新需求。

当前仓库只有 `MVP.md`（一份 6703 行的"生成器说明书"），P0–P6 的代码一行都没落地。本设计的任务分两段：

1. **落地**：把 MVP.md 里的 7 个生成器提取成真实项目
2. **修复**：按系统性评估，修掉让"探矿"这条链路不可信的 P0/P1 问题

## 二、目标（Goals）

1. 项目在 `pain-to-mvp/` 真实生成，结构完整（P0–P6）
2. 离线主干先通：`demo.py` 无网络跑出卡片 + 看板能显示
3. **真数据链路通**：B站关键词 → 评论 → 痛点 → 卡片，全链不断，数据不丢
4. Windows 环境（用户实际环境）能原生运行，无 emoji 乱码崩溃
5. 输出可信：评分不再恒定、卡片标题可读、无路径穿越漏洞
6. 最终用一个用户真实关键词端到端验收

## 三、非目标（Non-goals）

- **不自愈、不自优化**：heal_runner / optimizer / Journey 三个"假闭环"本轮不接入主流程。它们对探矿无直接贡献且会制造"系统在工作"的错觉。保留代码但标注"未接线"，或直接删档，二选一由执行时定
- 不新增平台适配器（小红书/抖音的 MediaCrawler 对接是独立工程，下轮）
- 不做部署、不做发布、不写 upstream PR
- 不追求 BERTopic 真跑（装不上就 TF-IDF 兜底，文档已承诺）

## 四、约束（Constraints）

- 用户环境：Windows / win32 / 非 git 仓库 → 脚本默认 PYTHONUTF8、bash 脚本降级为 PowerShell 或仅作参考
- B站爬取是唯一"免 key"主路径，WBI 签名是实现重点
- 所有修改落在 `pain-to-mvp/` 内，MVP.md 保持只读作为原始规格

## 五、已做决定（Builder 可自行决断的小事）

- 项目根目录定为 `MVP/pain-to-mvp/`（不污染 MVP.md 所在根）
- 生成器脚本从 MVP.md 按代码块提取，存放于 `generators/` 供复现
- 修复以"最小侵入的修正补丁"形式追加（`fixes.py` + patch），不改生成器原文，保证可复现生成
- 评分维度：competition/reach/ai_leverage 三个无数据来源的维度本轮改为"仅 LLM 可用时输出"，启发式只保留 demand 与 feasibility，总分用有效维度归一化
- Windows 兼容统一在入口 `sys.stdout.reconfigure(encoding="utf-8")`

## 六、留给 Builder 的开放项

- B站 WBI 签名：用 `bilibili-api-python` 库还是手写签名（倾向引入库，减少维护面）
- heal_runner 的最终处置（保留未接线 / 删除）
- 验收用的真实关键词（用户未指定，默认用 "独立开发" 或另一领域词）
